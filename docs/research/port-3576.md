# Port 1.0.0.3549 -> 1.0.0.3576 (2026-11-06)

Steam updated the game on 2026-11-06 05:53 to 1.0.0.3576 (PE 0x6AED2E85, SizeOfImage 0x13CC4000, 326,872,984 bytes),
in the middle of the native two-copy tests (tc42-tc44 ran on it without anyone noticing: the camera walker read
garbage because its globals had moved). The released Co-op+ (a82c1b48, made for 3549) switched itself off as designed.
The exe is archived in build/exe-archive.

Unlike 3527 -> 3549 (every address +0), the code moved this time. Tools: build/port3576.

## How each value was found
- `map_all.py` (portmap.py with OLD = 3549, NEW = 3576): every address of the 3549 table, code by its instructions
  (relative operands masked), data and vtables through the code that addresses them -> map_3576.json.
  All code sites: exactly one hit, head identical, except the ones below.
- Template copies (kActionLayersAdvance, kPending, both mid-function sites in two of 227 identical functions):
  the nearest hit was WRONG again (-0xE0 / -0x12F0), and so was "match the callee": the callee is a template
  copy too. What works: the 227 copies are emitted in the same order in both builds; the hook sites are in the
  64th and 66th copy in both, the whole block moved +0xD50 and every rip/call reference inside matches
  (tmpl5.py). 0x2331320 -> 0x2332070, 0x2331990 -> 0x23326E0, bytes identical.
- Vtables from RTTI (rtti_vt.py), CharacterControl slots 16/18/24 read from the new vtable.
- Heads with an embedded rip offset re-read: minimap decide, input-mode push (verify-port), the AI battle-type jmp.
- Troc opcode table (troc76.py): 1175 names in both, every id the same.

## FOUND: the aggro hook was on the wrong function since 3527
kCheckAIBattleType was 0x24C1C60 on 3527 and 3549. That is slot 1 of **AICondition_IsKeepAggro** (vtable 0x5C7CAD0),
not of AICondition_CheckAIBattleType (vtable 0x5C7CA60, slot 1 0x24C1D80). Both entries are a bare 5-byte jmp into
the copy protection, so the head check ("E9 xx xx xx xx") matched and the log said "CheckAIBattleType hooked".
The 3527 port re-read the 5 bytes at the same slot address of the wrong vtable. hist.py checks all archived builds:
3479 was right (0x24BE2F0 = CheckAIBattleType slot 1); 3527/3549 wrong. Effect on players: the "attack slots on the
copy" logic answered IsKeepAggro queries for enemies targeting the copy (enemies could drop the copy as a target
early); only while the copy was the target. Now taken from the RTTI on 3576: vtable 0x5C7CF78, slot 1 0x24C2B50,
head E9 DB 8A BA 0A. Lesson: a jmp-stub head proves nothing; map vtable slots by class name.
